# Fleet SOP — how the HD2 fleet works

**Status**: current operating procedure, 2026-10-23. Written after the throughput cycle that took
the fleet from six lanes to **twelve concurrent** (6 MiniMax + 6 Luna) on one host.
**Audience**: any firstmate or operator bringing up a surface, and anyone reading the board.
**Relation to `docs/DISPATCH-STANDARD.md`**: that standard (Captain order 2026-10-17) still owns
*how a lane is named, reviewed and reported*. This SOP owns *how a surface is run, how work is fed
it, and what must be true before we call it done*. Two conflicts are listed in §11 and are **not**
silently resolved here — both are Captain orders.

---

## 1. The shape of the fleet

A **surface** is a host that runs lanes (HD2Stack, Hetz, Elevate, KVM1, core-backup, controller).
Each surface has a **credential account**; the per-provider ceiling of six binds the **account**,
not the host, so two hosts sharing an account share one ceiling.

A **half** is one scheduler instance on a surface:

| | MiniMax half | Luna half |
|---|---|---|
| harness | `minimax-code` (mcode) | `codex` (codex-cli) |
| model | `minimax/MiniMax-M3.1-Flash` | `openai-codex/gpt-6-luna` |
| account | MiniMax (per account) | codex (per account) |
| ceiling | 6 | 6 |
| queue | the surface's backlog | its own queue file |
| state | the surface's `state/` | **its own** `state/` |

**Two halves on one host must not share `data/`, `state/`, lane ids, briefs, the in-flight set or
the queue.** Give the second half its own `FM_DATA_OVERRIDE` and `FM_STATE_OVERRIDE` and its own
queue file. That is what makes them independent — and what stops one half's accounting from
freezing the other.

## 2. The lane contract

A lane is a **named, bounded unit of work with one owner**. It is not done until:

1. its **artifact** exists on disk at a stated path;
2. the artifact's **last line** is `VERDICT: PASS <reason>` or `VERDICT: FAIL <reason>`, and the
   line before it is `NEXT:`;
3. the lane is **closed in the ledger** (`ops/lane-ledger.tsv`, state `DONE`, expiry empty) and on
   the claims board (`ops/LANE-CLAIMS.md`, expiry `-`).

**Dispatch is not a result.** A lane that was spawned has produced nothing. A lane that died has
lost its work and must be said so by name.

## 3. The brief is the contract

Every lane is briefed before it starts, and the brief carries all of these:

- **objective** — one sentence, the thing that must exist afterwards;
- **boundary** — what the lane may and may not touch, in the positive as well as the negative;
- **artifact path** — exactly where the deliverable goes, and **an absolute path outside the
  worktree** so it survives a worktree reclaim;
- **acceptance command** — how it proves the work;
- **stop condition** — when to stop and report rather than push on;
- **evidence rule** — *cite the file and line you actually read; write `UNVERIFIED` rather than
  inferring*. A claim with no citation is a defect in the report;
- **the decision-hold clause** — register each unresolved Captain decision with
  `bin/fm-decision-hold.sh hold` and pass the shared completion gate of the
  `decision-hold-lifecycle` skill, **inside the lane's own worktree**. This registration is the
  only repo write a read-only lane is authorised to make. (Learned the hard way: a brief that says
  "read-only, do not touch any repo file" **contradicts** the scaffolded completion gate, and the
  lane will fail visible rather than break either rule. Say which one wins.)
- **the verdict rule** — the report's last line is the verdict, and a package that cannot pass its
  gate says `FAIL` and says why.

## 4. Order of operations

1. **Plan** on paper first: the backlog row or task id, the project it belongs to, the artifact
   path, the acceptance command.
2. **Brief** it (§3).
3. **Spawn** it: one lane key per lane, minted in the naming gate's format
   `<harness>-<model-alias>-<host>-<task>` (§11).
4. **Monitor** it: a lane that is *alive* is not a lane that is *working*. Check CPU time, thread
   updates, or pane output — never process existence alone (§9, trap 1).
5. **Collect** the artifact the moment it lands, and **bundle the branch the moment the lane
   settles**. A worktree is disposable; a reclaim destroys the work.
6. **Close** it in the ledger and the claims board, then run the drift gate.
7. **Publish** the board and verify the served copy.

## 5. Running a second scheduler on a surface

Copy `docs/fan-out-kit/launcher-template.sh`, fill in **four variables** — harness, model, account
ceiling, and the half's own `data/`+`state/` root — and start it with `bin/fm-afk-launch.sh
start`. Never `nohup`, never `&`, never `disown`: the daemon must live in a tracked, non-visible
terminal that the launcher records and can tear down by exact id.

**All lane configuration lives in the launcher, in ENV**, never in the scheduler source. That is
what makes a half reversible: delete the launcher, stop the daemon, and the scheduler is
byte-identical to before.

**Do not edit the shared scheduler source to configure a half.** Four changes this cycle were
*necessary* and are the only kind worth making: a duplicated-task dispatch bug, a model id the
service refused, a hook-trust dialog that blocked every lane, and a worktree wait that could
expire while the worker ran. Each was backed up, each has a test, and each is in
`docs/fan-out-kit/traps.md`.

## 6. Reporting discipline

- **Starting**: one line naming the agent, the model, the task, the expected artifact.
- **Ending**: one line with the artifact path, its byte size, and its verdict line.
- **Failure**: say it immediately and name what was lost. A stopped lane must never pass as
  finished.
- **Never report a dispatch as a result.**

## 7. The board discipline

The **ledger** (`ops/lane-ledger.tsv`) is machine truth; the **claims board**
(`ops/LANE-CLAIMS.md`) is the human view; `ops/bin/fm-todo-sync.sh` refuses if they disagree.
Rules that hold:

- a claims row is **exactly seven pipe-separated cells**, lane id backticked, literal pipes escaped
  as `&#124;`, expiry in BST = ledger UTC + 1, and `DONE` rows carry expiry `-`;
- the **ask strip** is the only thing on the Captain's screen that needs him — a card is an ask
  only if it carries a decision;
- **the board must not ask for what is done.** When a package answers an ask, the ask is deleted,
  not annotated;
- **park what is superseded** rather than deleting it: the card stays visible as informational, so
  nothing is lost when the world moves (2026-10-23: Elevate's app-level asks were parked because
  the main site is being ported to WordPress — its **host-level** asks stayed, because a rebuild of
  the app does not close an open port on the host);
- **re-measure before re-deciding**: a ceiling, a quota, a risk rating and a capacity number all
  expire. The capacity note in this cycle expires **2026-10-25**.

## 8. Boundaries that do not move

Always a Captain gate: **spend, registrar, DNS, live deploy of client production, destructive or
irreversible acts, credentials**. Everything else — with a backup, a rollback and a recorded
rationale — is ours to decide and to do, and then to report.

**Never**: run `agent-secret-scan baseline`; read, print, hash or measure a credential value (or
any derived length, size, checksum or mtime — report present/absent, mode, owner); copy a managed
OAuth credential store between hosts; `rsync --delete`; delete-like shell keywords; `pkill -f`;
`docker volume rm`; `docker system prune`; force-push; `du` over `/`; `find /` without
`-maxdepth`; kill a pane that is provably working.

**Before every mutation**: a backup named `.bak-<tag>-<date>`, and the backup path recorded in the
artifact.

## 9. The traps — measure, do not assume

The full catalogue with detection and fix is `docs/fan-out-kit/traps.md`. The four that cost the
most this cycle:

1. **A live process that is not working.** Six codex lanes sat on a *"Hooks need review"* modal for
   35 minutes with **zero CPU and no model call**. Presence was not progress. Check CPU time or
   thread timestamps.
2. **The CLI accepted, the service refused.** `codex --model openai-codex/gpt-6-luna` is accepted
   by the CLI and answered with a **400** by the service; the bare `gpt-6-luna` answered. Prove a
   route with a **distinctive token reply**, never with a catalog line.
3. **A recorded failure with a live worker behind it.** The worktree wait expired while the
   worktree and the worker were created anyway, so the lane slot kept its old task and the daemon
   retried the same row.
4. **One cycle, six lanes, one row.** The in-flight set was built once per cycle and never
   refreshed after a spawn.

## 10. Verifying a fleet

`docs/fan-out-kit/verify-fleet.sh` is a **read-only census**: lanes per half from the lane metas
and their planning ids, live workers per harness, the two daemons' environments, and a fresh
quota reading. Run it after any change to a half, and before telling anyone how many lanes are
running. The board's numbers come from it, not from memory.

## 11. Two conflicts, flagged not resolved

| | older order (2026-10-17/16) | measured practice (2026-10-23) |
|---|---|---|
| fleet size | "never more than four lanes at once" | **twelve** (6 MiniMax + 6 Luna), per the Captain's 2026-10-22 directive |
| lane key format | `domain-surface-model-taskslug` | `<harness>-<model-alias>-<host>-<task>`, enforced by the naming gate (`bin/fm-lane-naming-check.sh`) |

Both are Captain orders. The naming gate is the live authority for lane keys, so the fleet follows
it; the four-lane cap is superseded by the twelve-lane directive. **Both need a one-line
amendment in `docs/DISPATCH-STANDARD.md` to become consistent** — flagged here rather than edited,
because that document is the Captain's contract and not ours to rewrite.

## 12. Changing this document

A lane may edit this SOP when it has measured something that changes the method. The edit ships
with the lane's evidence: what was measured, on which host, at which time, and what breaks if the
old text stays. The board's card says the change happened; this document says what changed.

enough to bring up a new surface from, and the two conflicts in §11 are the only items it cannot
resolve on its own.
