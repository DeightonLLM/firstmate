# Independent testability challenge: Core Distro V3 proposed acceptance spec

## Verdict

**The proposal is only partly testable from the local checkout.** A concrete set of static source-presence and syntax checks can be written for each PA-01–PA-10, and the repository's offline harness passes. Those checks do not test most stated user-visible or data-behavior outcomes: they establish that selected strings, actions, and source branches exist, not that those behaviors work. Several criteria also contain underspecified outcome words or sets. No criterion is ratified: the spec correctly marks all criteria proposed/unratified and explicitly requires product-owner confirmation for each. Do not interpret any local check as product acceptance.

The proposal's own final note records a concrete PA-04 ownership gap: `addLeads` does not first verify that `list_id` belongs to the caller. On the stated baseline, PA-04's “within an owned list” condition therefore cannot receive a clean result from the prescribed checks; if ratified literally, the criterion fails absent contrary evidence or a source correction.

This review did not evaluate infrastructure readiness as product acceptance. Brandon §20.1 remains separate and was not tested. No application source, tests, configuration, or project files were modified. No runtime, deployment, credentials, database, external service, browser, AnythingLLM, or container was used.

## Test-plan and spec-level gaps

1. **Marker presence is not behavior.** T1 and T2 are source/syntax checks. T3 requires a reviewer to interpret action-specific ownership; its grep output is explicitly insufficient. T4 requires recording outputs, reviewer and owner, but the spec says no canonical evidence location exists (§8). These can support only local source-contract reporting, not the user-visible verbs in the criterion titles.
2. **The planned checks are incomplete relative to their stated PASS rules.** Examples: PA-01 T2 omits reset hashing; PA-03/04 T2 checks action strings but ownership is only manual and PA-04's `addLeads` gap is already documented; PA-05 checks two aliases rather than a fully enumerated alias set and does not round-trip data; PA-07 lifecycle state/action presence does not show transitions or enforce concurrency; PA-10 does not check every role mapping. The full T2 script is in spec lines 380–478; T3 is lines 480–493.
3. **The product-policy boundary is explicit, not hidden.** Every PA row has an owner-confirmation need in the matrix (spec lines 116–125), and every detailed criterion repeats “Required” (129–351). The missing acceptance authority, baseline, and criterion-by-criterion decisions are explicitly listed in §8 and the blank ratification block §10. Thus no criterion can be silently treated as ratified; all ten still require product-owner authority before product acceptance.
4. **Infrastructure is separate.** §9 lists Brandon §20.1 as readiness work and says it cannot affect product results. None of those six readiness checks was run or inferred from the source checks in this review.

## Recommendation

Keep the document proposed/unratified. Report any future result as **local source-contract evidence**, not product acceptance. PA-01–PA-10 each admit source-presence checks, but the spec's prescribed checks do not establish the full behavioral claims. The clearest concrete fail is PA-04's owned-list condition on this baseline. Criteria with terms like “safely,” “preserves,” “bounded,” and “accessible” need their already-required owner-confirmed semantics before a complete pass/fail result can be claimed; this review does not supply or invent those semantics. Keep all §9 infrastructure readiness items outside the product verdict.
