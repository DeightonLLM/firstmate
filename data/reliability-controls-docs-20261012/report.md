## Bounded recovery runbook draft

1. **Reconcile before acting.** Use the already-emitted session-start digest. Treat endpoint presence and status-log lines as signals, not current truth; call `bin/fm-crew-state.sh <id>` for the targeted task. For a dead ordinary worker, use `.agents/skills/stuck-crewmate-recovery/SKILL.md`; for a secondmate, use `.agents/skills/secondmate-provisioning/SKILL.md` and reconcile only that home.
2. **Preserve task identity and owned state.** Check only the task's recorded endpoint/worktree inventory and active validation record. Do not create a second copy while ownership is ambiguous. Preserve uncommitted changes and commits. If custody cannot be reconciled, leave state intact and report the concrete conflict; no force, cleanup, or alternative tool path.
3. **Distinguish the facts.** Record request publication, delivery attempt/confirmation, worker processing, validation outcome tied to current code, and landed state separately. Acknowledgment is not authentic worker output; a `done` sentence or endpoint liveness is not a validation/landing proof. Use structured backlog/task state and artifact/head references.
4. **Close unresolved decisions before calling an investigation complete.** Read the full report and inventory actual captain choices. The `decision-hold-lifecycle` skill requires a durable keyed captain backlog item per unresolved choice and `bin/fm-decision-hold.sh complete` with all keys, or `--none` only after semantic review found none. This task's write authorization permits only its report and designated status file outside the isolated worktree; it does not authorize editing the originating backlog or task metadata. Therefore the primary must perform/authorize the originating-home completion command before this report can be called lifecycle-complete.
5. **Repair only after admission and custody.** Once the owning source/admission boundary is explicit, promote only the accepted smallest correction through its existing owner and delivery path. Verify it with its public executable interface, then update the owner doc and classified verification record only if the behavior actually changes. Do not write a new framework or duplicate policy.
